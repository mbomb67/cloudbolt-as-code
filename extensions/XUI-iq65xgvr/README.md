# Content Package Manager (XUI)

Adds **Admin > Custom Extensions > Content Packages**, where CB Admins define content packages: named lists of top-level blueprints, actions, plugins, shared modules, UI extensions, standalone parameters, and Runbooks workflows that ship together (forms and form functions are left out because they only sync with their parent). A package's details page lists its members, every dependency CloudBolt's own repository export writes with them, and the jobs of its last sync. A member shows red when it no longer exists on the appliance and amber when its Remote Source URL is not on the package's home repository and branch. A member or dependency whose folder holds a `README.md` on the branch its Remote Source URL points at gets a **Display documentation** button, which renders that README in a dialog; files are read from CloudBolt's clone of the repository, fetched at most once a minute.

- **Export** runs as a CloudBolt job, so the dialog returns at once and the job log records each member. The first export registers a plugin named "Content Package Manager: Export" whose code is this extension's `export_job.py`, so nothing else needs syncing. The job pushes each member with CloudBolt's own Push to repository (one commit per member, carrying its plugins, shared modules, and forms) as the user who started it, then commits the manifest to `packages/<PKG-id>/` with its README: written whole the first time, and on later exports only its member table is rebuilt, so members added since (a parameter, say) are listed and any text around the table stays. CloudBolt's push deletes each folder before rewriting it, so the manifest commit also puts back every markdown file those pushes deleted, and any file such a README links to, as it was on the branch before the export; the PR therefore shows no README deletions, and the details page lists what was restored. A second export of the same package is refused until the first finishes.
- **Sync** starts one CloudBolt sync job per member, chained so they run one at a time: shared modules and plugins first, blueprints last. A failed job holds the rest; fix the content, push it, and Rerun the failed job from its page to continue. As with any sync, a blueprint's group permissions are reset to what its metadata lists.
- **Parameters.** Source Control Repos cannot export a parameter on its own, so a package lists one as `parameters/CF-<id>` (any parameter on Admin > Parameters, such as an environment parameter an orchestration action reads) and the extension handles it with the serializer CloudBolt's blueprint export and import use for a blueprint's parameters. Export pushes the orchestration actions that generate the parameter's options, then writes `parameters/CF-<id>/CF-<id>_metadata.json` (definition, global options, defaults, constraints, field dependencies, and those actions as `orchestration_actions/HPA-*` references) plus a README the first time, in the manifest commit. Sync runs CloudBolt sync jobs for those actions with the other actions, then a job of the plugin "Content Package Manager: Sync Parameter" (code in `parameter_job.py`) per parameter, which creates it, or updates the parameter with the same name when refreshing, and links the actions. A parameter that already existed under another global ID keeps it, and the package resolves to it from then on. Environment and group assignments are not exported, and neither are option or default values of password, encrypted-text, or object types (network, storage, and similar).
- **Runbooks workflows.** A package lists a workflow of the Runbooks content as `runbook_workflows/SWF-<id>`. Export pushes the plugins its steps run, then writes `runbook_workflows/SWF-<id>/SWF-<id>_metadata.json` in the manifest commit, with the File Archives files its steps attach under `files/` (each up to 10 MB; a larger one is listed by checksum only). Sync runs CloudBolt sync jobs for those plugins, then a "Content Package Manager: Sync Workflow" job (`workflow_job.py`) that stores those files in File Archives (checked against their SHA-256 and CloudBolt's antivirus scan, added as a new version only when the newest differs) and then creates the workflow with the same ID or updates it. A different workflow with the same name is left alone and the job ends with a warning. A blueprint member whose Run Workflow build item pins a workflow (a default on its Workflow input, or on that question in the blueprint's custom form) carries it the same way without listing it. Group, environment, and configuration manager filters stay on each appliance. Both appliances need the Runbooks content. The picker lists Remote Scripts in their own section, because they are not shared plugins.
- **Import from repository** lists the `packages/` manifests on a branch and registers the chosen one by its PKG id, updating the package when that id is already registered, then opens Sync. Exported manifests are therefore the backup of the definitions.

Branch names must not contain a slash, because CloudBolt reads the branch from one part of each Remote Source URL. Each definition is one value of the parameter `content_package_store`, created on first use in the `content_packages` namespace so it stays off the Parameters list; deleting that parameter deletes every package. The same operations are available as JSON under `/xui/content_packages/api/` (CB Admin, session auth with CSRF). The extension adds URL paths, so restart the web server (`systemctl restart httpd`) after syncing it.
